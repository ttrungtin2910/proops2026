Applied Bash — Automate Git, Docker, AWS, Log Monitoring
Yesterday you learned the patterns. Today: can you take the real, repetitive DevOps tasks you've been doing manually — and turn them into scripts robust enough that someone else can run them without breaking anything?
The gap between a DevOps engineer who knows tools and one who operates at scale is automation. Every task done manually more than twice should be a script. Day 17 gave you the production-safety patterns; today you apply them to the four categories DevOps engineers automate first — Git, Docker, AWS CLI, and log monitoring. Tomorrow's deploy script is today's healthcheck.sh with three more steps. Day 24's CI/CD pipeline is today's deploy script wrapped in a GitHub Actions YAML.
The rule that drives the day
If you've done it manually twice, the third time it should be a script. By the end of today every command sequence you executed manually on Day 16 (push to ECR, deploy to EKS, verify, teardown) is a candidate for tomorrow's automation work.

Discovery chain — 8 questions
1
Write a single bash script that runs git pull → docker build → docker push → deploy, validates each step before moving to the next, and prints clear timestamped success/failure messages.
Help me build a deploy.sh that chains the four steps with proper error handling: (1) Header (Day 17 patterns): #!/bin/bash, set -euo pipefail, usage(), die() helper. (2) Phase 1 — git: `git pull --ff-only` (NOT plain pull — fails fast on diverged branch instead of forcing a merge). Capture the new HEAD: `COMMIT=$(git rev-parse --short HEAD)`. (3) Phase 2 — build: `docker build --platform=linux/amd64 -t myapp:$COMMIT .`. Tagging by commit hash, not :latest, makes every build traceable to a git state. (4) Phase 3 — push: `docker push [registry]/myapp:$COMMIT`. Must check exit code — a failed push that the script ignores breaks every deploy after. (5) Phase 4 — deploy: depends on the target. For EKS-style: `kubectl set image deployment/myapp myapp=[registry]/myapp:$COMMIT && kubectl rollout status deployment/myapp --timeout=120s`. For docker-compose: `docker-compose up -d --no-build`. (6) Logging: between every phase, `log "[$(date -u +%H:%M:%S)] phase X starting..."`. Use the log/err/die helpers from yesterday's memory file. (7) The two failure modes a manual process wouldn't catch: (a) git pull conflicted but you didn't notice — script catches via --ff-only failing, (b) docker push silently failed due to expired registry token — script catches via exit code check.
Tag images by commit hash (myapp:abc123f) not :latest. When you debug a production issue at 2am, you need to know exactly which commit is running. :latest tells you nothing.
2
Your script always builds and pushes — even when nothing changed. How do you skip the work when the current commit equals the last deployed one?
Make deploy.sh idempotent via commit-hash diff: (1) Where to store the last-deployed hash. A state file is simplest: `.last-deploy` in the repo (gitignored) or /var/lib/myapp/last-deploy. (2) Read the previous hash: `LAST=$(cat .last-deploy 2>/dev/null || echo "")`. The `|| echo ""` handles the first-run case where no file exists. (3) Compare: `if [[ "$COMMIT" == "$LAST" ]]; then log "no changes since last deploy ($COMMIT) — skipping"; exit 0; fi`. Exit 0 because skipping is success, not failure. (4) After successful deploy, write the new hash: `echo "$COMMIT" > .last-deploy`. ONLY after the deploy succeeded — if you write it before, a failed deploy looks succeeded next run. (5) Why this matters: every deploy script that gets used in cron or a scheduled job becomes idempotent eventually. Either you build it in from day one, or you add it after a 3am incident where the script ran 12 times and broke production. (6) Edge: what if someone manually deployed a different image? The .last-deploy file lies. Real production solutions write the deployed commit as a Kubernetes annotation or a git tag — but for today, the file is enough.
Idempotent = safe to run twice. The mental test: if a cron job runs your script every 5 minutes for an hour, does anything bad happen? If yes, it's not idempotent yet.
3
Add an AWS pre-flight check: before deploying, verify the target instance is running and the health endpoint returns 200. Abort the deploy if either fails.
Wire AWS CLI checks into deploy.sh as a preflight() function: (1) Instance state check: STATE=$(aws ec2 describe-instances --instance-ids "$INSTANCE_ID" --query 'Reservations[0].Instances[0].State.Name' --output text) [[ "$STATE" == "running" ]] || die "instance $INSTANCE_ID is in state: $STATE — aborting" (2) Endpoint health check: STATUS=$(curl -s -o /dev/null -w "%{http_code}" --max-time 5 "http://$HOST/health" || echo "000") [[ "$STATUS" == "200" ]] || die "health endpoint returned $STATUS — aborting" The `|| echo "000"` matters: if curl fails entirely (timeout, DNS failure), we still get a string we can compare. (3) Wrap both in a `preflight()` function called at the top of main(). If preflight fails, the deploy never starts. (4) `aws ec2 wait` for state-change loops: `aws ec2 wait instance-running --instance-ids $INSTANCE_ID` blocks until the instance is running. Useful when the deploy itself spins up infrastructure. (5) The deploy/preflight philosophy: every check you add is a 3am incident you don't have. Pre-flight is cheap; debugging a half-deployed system at 3am is not.
For HTTP checks, always use --max-time 5 on curl. Without it, an unreachable host can hang the script for 2 minutes (default TCP timeout). Bounded waits everywhere.
4
The script does git, docker, AWS, deploy. A teammate runs it, hits an error, has no idea which step failed. Add structured logging — every step prints with timestamp and status.
Build a structured logging pattern for the deploy script: (1) Convention: every phase emits two lines: [2026-04-27T14:30:00Z] [git] START pulling latest [2026-04-27T14:30:01Z] [git] OK at abc123f or on failure: [2026-04-27T14:30:01Z] [git] FAIL fast-forward not possible — branch diverged (2) Helper functions: _ts() { date -u +%Y-%m-%dT%H:%M:%SZ; } start() { echo "[$(_ts)] [$1] START $2"; } ok() { echo "[$(_ts)] [$1] OK $2"; } fail() { echo "[$(_ts)] [$1] FAIL $2" >&2; exit 1; } (3) Phase pattern: `start git "pulling latest"; git pull --ff-only || fail git "$?"; ok git "at $COMMIT"`. (4) Why structured: a CI log viewer can grep for FAIL across thousands of lines. A grep for `\[git\] FAIL` shows you exactly which deploys broke at the git phase. (5) Even better — JSON logging if your log aggregator supports it: `printf '{"ts":"%s","phase":"%s","status":"%s","msg":"%s"}\n' "$(_ts)" "$1" OK "$2"`. Day 18 stays text — JSON is a nice-to-have for production.
Always emit logs to stdout (normal) and stderr (failures). When the script's stdout is captured to a file but stderr goes to the terminal, the human sees the failure even though the log captures everything.
5
Write a separate script log-monitor.sh that watches a log file for ERROR patterns and alerts. Avoid alert spam by deduplicating repeated errors.
Build a log monitoring script with deduplication: (1) Real-time tail: `tail -F /var/log/app.log` — capital F follows the file even after rotation. Lowercase -f stops following if the file is rotated, which breaks log monitoring constantly. (2) Filter for ERROR lines: pipe through grep: tail -F /var/log/app.log | grep --line-buffered -E '\[ERROR\]|\bERROR\b' | while read -r line; do ...; done `--line-buffered` matters in pipes: without it grep buffers lines and your alerts come in batches, not real time. (3) Deduplication: hash each error message, store the hash in a file with a timestamp: key=$(echo "$line" | sha256sum | cut -c1-12) if grep -q "^$key " "$DEDUP_FILE" 2>/dev/null; then continue # already alerted fi echo "$key $(date -u +%s)" >> "$DEDUP_FILE" send_alert "$line" (4) Periodic dedup-file pruning: entries older than 1 hour can be re-alerted. Add a cleanup step at script start: awk -v cutoff=$(($(date +%s) - 3600)) '$2 > cutoff' "$DEDUP_FILE" > "$DEDUP_FILE.tmp" && mv "$DEDUP_FILE.tmp" "$DEDUP_FILE" (5) The send_alert function: today, just `echo` to a file. In a real env, curl to a webhook (Slack, Discord, PagerDuty). Same pattern. (6) Why dedup: without it, an error in a tight loop fires 10,000 alerts in a minute. Engineers turn off alerts. Production goes down silently next time.
Use tail -F (capital F), not tail -f (lowercase). The capital follows through file rotation. Trainees who use -f spend an hour wondering why the monitor stopped working overnight.
6
Schedule the log monitor to run every 5 minutes via cron. The two things that always break cron jobs: PATH and environment variables. How do you prevent both?
Cron crash course + safe cron-script template: (1) crontab syntax: `MIN HOUR DOM MON DOW command`. `*/5 * * * *` = every 5 minutes. `0 2 * * *` = 2am daily. View current: `crontab -l`. Edit: `crontab -e`. (2) Why cron jobs fail: cron runs scripts in a minimal environment. No ~/.bashrc. PATH is usually `/usr/bin:/bin` only. HOME may be unset. So your beautifully-working script fails with "jq: command not found" or "AWS credentials missing". (3) Fix #1 — explicit PATH at top of script: export PATH="/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin" Or in the crontab itself: PATH=/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin */5 * * * * /home/me/scripts/log-monitor.sh (4) Fix #2 — explicit env vars / source a profile: */5 * * * * . /home/me/.profile && /home/me/scripts/log-monitor.sh Or set vars inline: `*/5 * * * * AWS_PROFILE=prod /home/me/scripts/log-monitor.sh`. (5) Capture cron output. Default cron mails it nowhere. Redirect explicitly: */5 * * * * /home/me/scripts/log-monitor.sh >> /var/log/log-monitor.log 2>&1 (6) Test before scheduling: run the script with cron's restricted env: `env -i PATH=/usr/bin:/bin /home/me/scripts/log-monitor.sh`. If it works under that, cron will too.
First test the script under env -i PATH=/usr/bin:/bin SHELL=/bin/sh /path/to/script.sh. That simulates cron's environment exactly — if it works, cron will work; if it fails, cron will fail in the same way.
Always redirect cron output to a log file. >> /tmp/myjob.log 2>&1. Without it, errors disappear into the void.
7
Add a --dry-run flag to deploy.sh. In dry-run mode it prints what it would do but doesn't change anything. Why is this essential for any script that touches production?
The dry-run pattern: (1) Parse flags. Simple form: DRY_RUN=0 while [[ $# -gt 0 ]]; do case "$1" in --dry-run) DRY_RUN=1; shift ;; --help) usage; exit 0 ;; *) break ;; esac done (2) The execution pattern: run() { if [[ $DRY_RUN -eq 1 ]]; then echo "DRY-RUN: $*" else "$@" fi } Then every change becomes: `run docker push myapp:$COMMIT` instead of `docker push myapp:$COMMIT`. (3) Read-only commands (git rev-parse, aws describe-*) should NOT go through `run` — they're safe to execute in dry-run mode and the output is needed for downstream logic. (4) Why dry-run is non-negotiable: every production-grade DevOps tool has it (terraform plan, kubectl --dry-run=client, helm install --dry-run). It's how you review changes before they happen. Without dry-run, "let me see what this would do" is impossible without actually doing it. (5) The strongest validation: run with --dry-run on a fresh checkout, scan the output, then run for real. The output should match. Dry-run that diverges from real execution is worse than no dry-run.
Treat dry-run as a feature, not a bolt-on. If your script does 8 things, all 8 must be wrapped through run .... One unwrapped command and dry-run is a lie.
8
Write skills/bash-automation.md — the playbook for taking ANY repetitive DevOps task and turning it into a production-safe bash script. What's the six-question design checklist?
Help me write skills/bash-automation.md. Unlike yesterday's memory file (reference), this is a SKILL — a procedure my agent invokes when I say "automate this". Structure: 1. Trigger condition: when to apply this skill - Any task done manually 2+ times - Any task that runs in cron, CI, or scheduled - Any task whose failure costs money or sleep 2. Six design questions to answer BEFORE writing line one: Q1. What does the script do, in one sentence? Q2. What inputs does it take? Which are required vs optional? Q3. What can go wrong at each step? (network, permission, missing tool, conflicting state) Q4. What should it check BEFORE making changes? (preflight) Q5. How does it report status — success and failure separately? Q6. Is it idempotent — safe to run twice? 3. Standard script skeleton (copy-paste template): - Header: shebang, set -euo pipefail - Constants (readonly UPPERCASE) - Helpers: _ts, log, err, die, run (for dry-run) - usage() - preflight() — tool checks, AWS state, network reachability - main() — orchestrates phases - Phase functions: phase_git(), phase_build(), phase_deploy() - Last line: main "$@" 4. Four canonical patterns from today: - Deploy chain (git → build → push → deploy with idempotency) - AWS preflight check - Log monitor with dedup - Cron-safe scheduling 5. Five pitfalls + fixes — yours from today, not generic. 6. The dry-run rule: every change wrapped in `run`, every read-only command bare. Format: short bullets and code blocks, no prose paragraphs.
A skills file differs from a memory file: memory is reference data ("here's the syntax for X"), skill is a procedure ("when I say automate this, do this checklist first"). Frame the file in the imperative — "do this", not "this is".
