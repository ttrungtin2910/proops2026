Terraform + Ansible — Your First Infrastructure as Code
Yesterday's deploy script changed infrastructure manually, step by step. What if the infrastructure itself — the EC2 instances, security groups, networking — could be declared in a file, version-controlled, and reproduced exactly from scratch in 90 seconds?
Bash scripts describe a procedure. Terraform describes a desired state. The difference is enormous in production: a script run twice can create duplicate resources, leave orphans, and leave you guessing what exists. Terraform's state file tracks every resource it manages — terraform plan shows you exactly what will change before anything happens. Ansible fills the other half: once Terraform provisions the machine, Ansible configures what runs on it (packages, files, services). Together they replace the AWS console click-ops that was your workflow on Day 11 — and they run the same way on your laptop, in CI, and in a teammate's environment.
The mental split that drives the day
Terraform answers: "what infrastructure exists?" (EC2, VPC, security groups, EKS clusters). Ansible answers: "what is installed and running on it?" (nginx, Docker, app config files). Bash handles the glue between them. You will use all three; the skill is knowing which one to reach for first.
The two-tool mental model
Day 11 you built an EC2 instance by clicking the console + running AWS CLI commands. Those actions are not reproducible — a teammate can't run them from your notes. Today you write files instead. Both tools use declarative configuration; the difference is what they declare.
Tool 1
Terraform
Declares infrastructure — VMs, networks, DNS, clusters
HashiCorp Configuration Language (HCL) — human-readable
Tracks state in terraform.tfstate
Core loop: init → plan → apply → destroy
Plan = built-in --dry-run. Always run plan first.
Idempotent by design — running twice changes nothing if state matches
Tool 2
Ansible
Declares configuration — packages, files, services, users
YAML playbooks + inventory of hosts
Agentless — connects over SSH, no daemon on the target
Core files: playbook.yml, inventory.ini
Runs on Linux/macOS control node — use WSL2 on Windows
Idempotent tasks — running twice installs nothing new if already present
Typical flow on a new server:
terraform apply → EC2 created, IP output → ansible-playbook playbook.yml -i inventory.ini → nginx installed + running → your app is live.
Cost safety — read before touching AWS
All EC2 instances in today's lab use t3.micro (Free Tier eligible). Set a phone alarm before terraform apply — run terraform destroy at end of session. Unlike Day 16, Terraform tracks every resource it created. terraform destroy removes all of them in one command. Verify with aws ec2 describe-instances --query 'Reservations[].Instances[?State.Name!=`terminated`]' after destroy.

The key insight: Bash describes steps. Terraform describes the end state. Steps are hard to diff, hard to audit, and dangerous to re-run. End-state files version like source code and show exactly what changed between runs.

A data source reads existing AWS state (like aws describe-images) and makes the result available in your config. A resource creates or manages AWS state. Never hardcode AMI IDs — they change per region and when Amazon releases patches.

3
What is terraform.tfstate? Open it after your first terraform apply. What does it contain? Why would losing it be a serious problem?
Explain the state file to me deeply: (1) What is in terraform.tfstate? Open it with `cat terraform.tfstate | python3 -m json.tool | head -60`. What resource types, IDs, and attributes does it track? Is the instance_id in there? The private IP? The AMI ID? (2) What does Terraform do with the state file on the next `terraform plan`? Walk through: it reads state → calls AWS API to get current real state → diffs the two. What is "state drift" — when the state file disagrees with what AWS actually has? (3) What happens if you delete terraform.tfstate and run terraform plan? (Answer: Terraform thinks nothing exists, plans to CREATE everything from scratch, which would create duplicate EC2 instances.) This is a real production incident pattern. How do teams prevent it? (4) Three state file rules: Rule 1: Never commit terraform.tfstate to git (it contains resource IDs, may contain secrets). Rule 2: In production, store state remotely (S3 backend + DynamoDB lock). Why locking? Rule 3: Never edit the state file manually. Use `terraform state` commands. (5) The S3 backend (concept only — don't implement today): terraform { backend "s3" { bucket = "my-tfstate-bucket" key = "proops2026/terraform.tfstate" region = "ap-northeast-1" dynamodb_table = "terraform-locks" } } Why DynamoDB for locks? (Prevent two engineers from running apply simultaneously.) Save a summary of these rules in memory/iac-basics.md — state section.
The state file is Terraform's memory. Without it, Terraform is blind to what it already created. In production, losing the state file = losing control of your infrastructure. Remote backends (S3) + locking (DynamoDB) prevent both loss and corruption.

Extract instance_type, region, and your name into Terraform variables with defaults. Test overriding instance_type at the command line without editing main.tf.
Refactor main.tf with proper variable declarations: (1) variables.tf — separate file for variable declarations: variable "aws_region" { description = "AWS region" type = string default = "ap-northeast-1" } variable "instance_type" { description = "EC2 instance type" type = string default = "t3.micro" } variable "owner_name" { description = "Your trainee ID (e.g. quyet_nc)" type = string } (2) Reference variables in main.tf: provider "aws" { region = var.aws_region } resource "aws_instance" "app" { instance_type = var.instance_type tags = { Owner = var.owner_name } } (3) terraform.tfvars — supply default values without editing code: owner_name = "your_name_here" instance_type = "t3.micro" Why is terraform.tfvars gitignored? (May contain account IDs, environment names.) (4) Override at CLI: `terraform plan -var instance_type=t3.nano` Watch the plan show the change from t3.micro to t3.nano. Variables make your Terraform modules reusable. A module with hardcoded region and instance type is a script with extra steps. A module with proper variables can be used for dev, staging, and prod by changing a single .tfvars file.
5
Run terraform apply. Verify the EC2 instance appears in the AWS console with your tags. Then understand what terraform destroy does — and why it's safer than manual deletion.
Guided apply + verify + understand destroy: (1) Apply: terraform apply When it asks "Do you want to perform these actions?" — read the plan summary again. Type "yes" only after reading it. This is the one place where Terraform slows you down intentionally. (2) Verify (after apply completes): - Check the output: `instance_public_ip = "x.x.x.x"` - AWS console: EC2 → Instances → filter by tag Owner=your_name → verify state=running, tags correct - CLI: `aws ec2 describe-instances --filters "Name=tag:Owner,Values=your_name" --query 'Reservations[].Instances[].[InstanceId,State.Name,Tags]'` (3) Run terraform plan again — on already-created infrastructure: What does the output say? Why "No changes"? This proves idempotency — running apply twice creates nothing new. (4) Now understand destroy: terraform destroy --target aws_instance.app Or full destroy: terraform destroy What does Terraform read to know what to delete? (the state file) What does the plan section show before it deletes? (5) Why destroy is safer than manual console deletion: - Terraform reads the state, deletes in dependency order (e.g., removes SG only after instance is terminated) - After destroy, state file is cleared — no orphan state records - Compare to Day 16: you manually deleted ELBs, EBS volumes, NAT gateways one by one. Destroy automates all of that. DO run destroy at end of today's session. Phone alarm rule still applies.
After terraform apply, never manually delete a resource in the console. If you do, the state file still thinks it exists, and the next plan will show no changes — even though the resource is gone. Always manage Terraform-created resources through Terraform.
Set a phone alarm for the end of your session. Run terraform destroy before logging off. Verify with AWS CLI that no instances are running. t3.micro costs ~$0.01/hr — small, but left running for a week = $1.68, and more importantly it's a habit you must build before managing production infra.
6
What is Ansible? How does it differ from Terraform? Set up Ansible in WSL2, write an inventory file pointing at your EC2 instance, and verify you can ping it.
Ansible intro — concepts first, then hands-on: (1) The mental model: Terraform: I want an EC2 instance to exist. (Infrastructure provisioning) Ansible: I want nginx installed and running on that EC2 instance. (Configuration management) Both are declarative and idempotent. The split: Terraform manages AWS objects, Ansible manages OS and software. (2) Key concepts: - Inventory: a file listing the hosts Ansible should manage (IP addresses or hostnames) - Playbook: a YAML file describing what to do on those hosts (tasks in order) - Task: one action (install nginx, copy a file, start a service) - Handler: a task that only runs when notified (e.g., restart nginx only if its config changed) - Module: the built-in action verb — `apt`, `yum`, `copy`, `service`, `template` - Agentless: Ansible SSHes in; nothing installed on the target machine (3) Install Ansible in WSL2 (Ubuntu): sudo apt update && sudo apt install -y ansible ansible --version (4) Inventory file (iac/ansible/inventory.ini): [webservers] ec2-day19 ansible_host= ansible_user=ec2-user ansible_ssh_private_key_file=~/.ssh/your-key.pem (5) Connection test (verify SSH works before writing a single playbook): ansible webservers -i inventory.ini -m ping Expected output: ec2-day19 | SUCCESS => { "ping": "pong" } If this fails, fix SSH before moving to Q7. Common causes: - Security Group blocks port 22 → add inbound SSH rule - Wrong ansible_user (Amazon Linux 2023 = ec2-user, Ubuntu = ubuntu) - Key permissions: `chmod 400 ~/.ssh/your-key.pem`
Ansible is Linux/macOS only — it must run from WSL2 on Windows. The control node is your laptop (via WSL2); the managed node is the EC2 instance. No Ansible daemon runs on EC2 — it's pure SSH.
